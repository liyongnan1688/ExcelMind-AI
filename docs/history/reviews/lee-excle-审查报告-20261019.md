## 二、现存问题清单

### P0 — 会直接影响正确性或可维护性，建议下一轮优先处理

#### P0-1 决策器是中文正则关键词，误判代价不对称

- **位置**：`web/src/services/decisionEngine.ts:106`
- **现象**：`heavyKeywords` 包含「计算 / 加总 / 排序 / 过滤 / 修改 / 生成图表」等词，命中即进入 B 轨（VBA + 整本快照）。决策器只在 `requestMode === 'AUTOMATION'` 时生效，且关键词全部为中文。
- **影响**：
  - 用户问"这个公式怎么计算"→ 被判为 B 轨，白跑一次快照 + VBA 生成。
  - 英文请求全部落到 CHAT。
  - A 轨短路是安全的（只读），但 B 轨由正则直接决定、无二次确认，属于**用关键词代替意图理解**。
- **建议**：决策器降级为"建议"，B 轨执行前必须有一次显式确认（或由模型在结构化输出里选轨）；A 轨可以保持短路。

#### P0-2 工具定义存在三处真相，且无参数校验

- **位置**：`decisionEngine.ts` 的 `suggestedMcpCall`、`mcpClient.ts:168-280` 的 if 链、`NativeBridge.cs` 的 `switch case`
- **现象**：同一个工具名（如 `excel_get_workbook_overview`）在三个文件里各写一遍；参数直接 `args.xxx` 取值，没有类型/必填校验。
- **影响**：加第 4 个工具要改三处，漏改一处就出现"决策器说能调、网关说不认识、宿主不处理"的静默失败。
- **建议**：抽一张 `ToolDescriptor` 表（名字、参数 schema、权限、是否可逆），三处都从这张表派生；参数进 handler 前统一校验。

#### P0-3 名为 MCP，实为本地 if/else 分派

- **位置**：`mcpClient.ts` 全篇
- **现象**：没有 JSON-RPC、没有 transport、没有 server 概念，本质是一个本地函数表加一段"Tool Schemas"文本注入。
- **影响**：命名会误导后续开发（包括 AI 协作者）；将来要接真 MCP（外部 server、stdio/SSE transport）时需要重写，且现在的接口形状会限制演进。
- **建议**：要么改名为 `localToolGateway`，要么按 MCP 的真实形状实现（Pi 的 `mcp.ts` / `mcp-transport.ts` 可参考）。

### P1 — 影响可信度与可回归性

#### P1-1 工具结果没有 `verified` 字段，但 UI 文案已宣称"验证通过"

- **位置**：`web/src/components/ExecutionCard.svelte` 新增按钮 title：*"将本次执行验证通过的代码一键沉淀为本地宏库"*
- **现象**：代码里没有把验证状态传下来，按钮文案先于能力。
- **影响**：用户会以为"存为常用宏"只收已验证代码，实际不区分；这是信任层的空头承诺。
- **建议**：工具结果强制 `verified: "full" | "partial" | "none"`（缺省 `none`）；"存为常用宏"仅在 `full` 时可点；UI 三态显示（已验证/部分/未验证）。

#### P1-2 压缩会洗掉证据

- **位置**：`compaction.ts:116-190`（`buildStructuredSummary`）
- **现象**：摘要靠正则抓 Sub 名、表名、"必须/严禁/格式"类规则句。失败步骤、快照 id、验证状态**都不进摘要**。
- **影响**：对话越长，模型越依赖"摘要记忆"陈述结果，出现"我已完成"但无据可查的情况——这正是上次分析 Pi 时指出的同一个洞。
- **建议**：把证据设为**不可压缩**（快照 id、失败步、verified 状态、错误类型），只压缩解释性文本。

#### P1-3 测试覆盖不足，且存在"测副本"的假测试

- **位置**：`test_suite_unit.cjs` 新增第 20 组「Cache-Safe Prompt & Compaction Pipeline Suite」
- **现象**：测试里把 system prompt **复制粘贴**了一份再断言字节恒定，测的是副本，不是 `llm.ts` 的实现；`FormulaAuditService` / `decisionEngine` / `compaction` / `mcpClient` 四个新模块零测试。
- **影响**：改动提示词后测试照样绿，回归保护是假的。
- **建议**：测试从构建产物或真实模块读取（CJS 可读 `web/src` 的编译产物），至少补三个新模块的最小用例。

### P2 — 仓库卫生与工程规范

#### P2-1 工作区未提交，发布与源码脱节

- **现象**：`src/FormulaAuditService.cs`、`compaction.ts`、`decisionEngine.ts`、`mcpClient.ts` 未跟踪；`NativeBridge.cs`、`llm.ts`、`App.svelte`、`ExecutionCard.svelte`、`ChatInput.svelte`、`bridge.ts` 已改未提交；`bin/LeeExcel.dll` 已改。
- **影响**：v1.3.0 的发行包源码状态 ≠ 当前工作区，出问题无法从 tag 复现。
- **建议**：先把这批改动整理成一次（或几次）语义化提交，再谈下一轮。

#### P2-2 `node_modules` 的 pnpm 状态文件被 git 跟踪

- **现象**：`git status` 出现 `web/node_modules/.modules.yaml`、`.pnpm-workspace-state-v1.json`、`.pnpm/lock.yaml`。
- **建议**：`.gitignore` 收口 `web/node_modules/`，`git rm -r --cached` 掉已跟踪部分。

#### P2-3 排版公约硬编码在提示词里

- **位置**：`llm.ts` 的 `buildStaticAutomationSystemPrompt`
- **现象**：千分位、红字负数、表头色值、边框、对齐全部写死在字符串里。
- **影响**：改一条企业规范要重新编译 + 打包 + 重新分发；不同客户/项目无法差异化。
- **建议**：外置为 `Conventions` 数据文件（JSON/MD），启动时读取并拼进静态前缀的**尾部**（保证前缀仍可缓存）。

## 三、改进建议（分阶段，含验收标准）

### 阶段 0：收口（半天）

1. 提交工作区全部改动，打 tag。
2. `.gitignore` 收口 `node_modules`。
3. **验收**：`git status` 干净；从 tag 能复现当前二进制。

### 阶段 1：把"三处真相"合成一处（2–3 天）

1. 建 `ToolDescriptor` 表（C# 侧权威，前端从 bridge 拉取或由构建生成 TS 类型）。
2. `NativeBridge` 只保留一个通用 `InvokeTool(name, args)` 入口；参数统一校验。
3. `decisionEngine` 的 `suggestedMcpCall` 改为按 descriptor 生成，不再手写工具名。
4. **验收**：新增第 4 个只读工具时，只改 1 个 descriptor + 1 个 handler；`mcpClient.ts` 零改动。

### 阶段 2：把"真"补上（3–5 天）

1. 工具结果增加 `verified: full | partial | none`，缺省 `none`。
2. `ExecutionCard` 三态渲染；"存为常用宏"仅在 `full` 时可点。
3. `compaction` 把证据字段列入白名单，永不压缩。
4. **验收**：任一次写入操作，UI 上能明确看出验证状态；压缩 3 轮后，早期快照 id 仍可查。

### 阶段 3：决策器与提示词数据化（3–5 天）

1. 决策器降级为建议，B 轨执行前显式确认。
2. 排版公约外置为数据文件，拼进静态前缀尾部。
3. **验收**：改一条排版规范不需要重新编译；英文请求不再一律落 CHAT。

### 阶段 4（可选）：验证层与回归

1. 测试改为读取真实模块/构建产物，补四个新模块用例。
2. 增量恢复日志替代整本快照（工作簿 > 20MB 时收益明显）。

## 四、与 Pi for Excel 的对照（简要）

| 维度 | Pi for Excel | lee-excle（当前） |
|---|---|---|
| 工具层 | 67 个单一职责模块 + registry + execution-policy | 三处硬编码，无 registry |
| 上下文 | 蓝图 / 选区 / 变更追踪三层 + 预算裁剪 | 蓝图 + 选区，**无变更追踪** |

**取长补短的方向**：抄它的 registry / 变更追踪 / 验证字段；不要抄它的托管形态、框架和 OAuth。
